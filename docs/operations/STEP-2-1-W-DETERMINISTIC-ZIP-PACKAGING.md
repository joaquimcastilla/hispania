# Step 2.1-W — Deterministic ZIP Packaging

**Status: PARTIAL; hosted acceptance found two build-input reproducibility issues, now corrected locally and awaiting a rerun.** This record is scoped to the Step 2.1-W candidate and does not change the Step 2.1 final acceptance decision.

## Scope

The common ZIP contract applies to complete production artifacts from `tools/publish-production.ps1` and Platform-only artifacts from `tools/publish-platform-only.ps1`. It does not change application contents, installation semantics, signed module extension packages, the production Linux `.tar.gz` archive, runners, Coordinator services, or release configuration.

The production workflow's Linux `.tar.gz` is a separate archive path generated by GNU `tar`; it is not covered by ZIP identity evidence. `tools/package-extension.ps1` packages signed extension payloads under their own manifest/signature contract and remains unchanged.

## Root cause

Phase 25 run [38325713684](https://github.com/joaquimcastilla/hispania/actions/runs/38325713684) recorded identical trees (186 files) and identical manifest SHA-256 (`d670a11e1c93561107a3dfbdfb0c3ce3ad5f515508e3a20d992a96f0ee5fe58c`) but different ZIP hashes: `eb00c109b46f8205aa3b25fbbd231015491a63e659ebba9962454565549d4c51` and `d32ec5595ae83f115b106b2d8bca4ff0c961aafca516ba406772f6c2ff380ad4`. The uploaded evidence contains the first ZIP, not the second, so a historical entry-by-entry comparison is unavailable.

The inspected historical ZIP contained many distinct entry timestamps. A controlled reproduction using identical names and bytes but different source mtimes produced hashes `7f76b032b8e9c5d3ed17ccf28c443b924dc75f69e33e5c3e116f2fe003152f7c` and `ec123a752dc6c5dff8ec94dac722bd2f9c597c953c8c981c8c30ffa6c7f532d5`; after matching source timestamps, both were `7f76b032b8e9c5d3ed17ccf28c443b924dc75f69e33e5c3e116f2fe003152f7c`. This demonstrates that the old archive envelope embedded varying filesystem timestamps; opposite file-creation order did not prevent equality after timestamp normalization in the controlled reproduction. `Compress-Archive` also did not preserve executable permission on the Linux installation script.

The first hosted Step 2.1-W run, [38641818353](https://github.com/joaquimcastilla/hispania/actions/runs/38641818353), uncovered an additional defect before archive comparison: independent clean checkouts produced 107 differing published file hashes per RID. Inspecting `deployment/Hispania.Hosting.dll` showed the first byte difference in the PE COFF timestamp field (offset 136 in the captured file). The publishers had not explicitly enabled deterministic CI compilation. This changed the artifact manifest's file hash inventory and therefore the ZIP bytes as well. Both publishers now set `Deterministic=true` and `ContinuousIntegrationBuild=true` on every production publish/build invocation; the ARM64 host-native verifier build receives the same settings. A local two-checkout .NET 10 probe with those properties and the same PathMap produced identical DLL hashes (`bcb6f13b04b063bfcb41b17b1d671cf599f0bcc15ccb9761133f1f377996d78c` on both checkouts).

The second hosted run, [38642765016](https://github.com/joaquimcastilla/hispania/actions/runs/38642765016), reduced the tree difference to one file on all three RIDs: `server/Hispania.Server.staticwebassets.endpoints.json`. Its 80 endpoint records embedded varying `Last-Modified` dates derived from freshly generated `apps/web/dist` files. The publisher now uses the common .NET tool to set those generated HTTP `Last-Modified` values to the source commit timestamp before hashing. The tool has a fixture regression proving otherwise identical endpoint manifests become byte-identical while preserving routes. Full product matrix confirmation is pending.

The failed run's ZIP pairs were `linux-x64` `8598ed5d2f0d236ae598c2017fa058533a8202208a7be641ffffe3470f0dd060` / `457c1b513f323b5992fc17e3a27b53ca9a26a3720d5b574a6ad5017db9a9f67f`; `linux-arm64` `2dd42171edac9b1bf095d67286eacc848650c0d3e2ac0e31901a76644d9cbbac` / `351f0045611e97e6d91a3b0b1ca7d0c126b6e4b2551615dcd7c4a20ccc18731a`; `win-x64` `3f993564dbe11c5e1662b780086a1a1bd077d47fe1e653fa70e84393fab27c05` / `12609a74bbe0a93791659b229bac31b9274b242f11f2c8141d58e575961b5931`. ## ZIP contract

`tools/deterministic-zip` is the one packer used by both artifact publishers:

- Entry paths use `/`, exclude the source root, sort with ordinal comparison, include empty directories, and reject unsafe paths, case collisions, links/reparse points, and output inside the source tree.
- Every entry gets the ZIP epoch timestamp `1980-01-01 00:00:00`.
- Entries use the ZIP **Store** method (`CompressionMethod = 0`) through .NET `ZipArchive` with `CompressionLevel.NoCompression`. This eliminates compressor variability between operating systems at the cost of larger archives.
- Unix metadata is canonical: directories `0755`, non-executable files `0644`, executable files `0755`. Executability is derived from source mode on Unix. Windows packages use stable regular-file attributes.
- Publishers write the SHA-256 sidecar only after the archive is finalized.

The full publisher now accepts `linux-arm64` as well as `win-x64` and `linux-x64`; ARM64 manifests identify `aarch64` and the ASP.NET Core 10 ARM64 runtime prerequisite. This is cross-publication/package validation only; it does not claim native Complete ARM64 runtime or WindowsServices support.

## Local evidence

`dotnet test tests/deterministic-zip/Hispania.DeterministicZip.Tests.csproj --configuration Release` passed 12/12 tests on Windows with .NET SDK 10.0.401. The tests prove equal archive bytes for same file trees with different creation order and modification times; fixed entry ordering, DOS timestamp, Store method, empty directories and Unix modes; UTF-8 names; unsafe/absolute/traversal/reserved paths; known temp/editor residue; output containment; and link rejection. Case-collision behavior is exercised on Linux because Windows filesystems cannot create case-only sibling names.

The hosted Phase 25 matrix is enabled through `deterministic_zip_only: true` and uses:

| RID | Hosted runner | Acceptance |
|---|---|---|
| `win-x64` | `windows-2025` | Two clean independent checkouts/builds, tree and ZIP SHA comparison, metadata and install/`--check` |
| `linux-x64` | `ubuntu-24.04` | Two clean independent checkouts/builds, tree and ZIP SHA comparison, metadata, install/`--check`, execute-bit check |
| `linux-arm64` | `ubuntu-24.04` | Two clean independent cross-publishes, tree and ZIP SHA comparison, ARM64 manifest, host-native Deployment CLI verifies target artifact, execute-bit check |

The deterministic-only input skips Phase 25's pre-existing self-hosted Linux job. Workflow access remains limited to the existing authorized repository, actor, candidate branch, `workflow_dispatch`, and exact candidate SHA checks; permissions remain `contents: read`, checkout credentials are not persisted, and no production secrets are used.

The workflow uploads each RID's first ZIP and checksums/manifest/build evidence. The job summary records runner OS, RID, source SHA, SDK version and hashes. Hosted results are pending; no local result should be represented as cross-platform acceptance.

## Open limitations

- The no-compression ZIP increases archive size substantially relative to `Optimal`; record actual matrix sizes before deciding whether to retain it.
- The independent hosted builds use the same host OS for a given RID. They prove byte reproducibility on the designated hosted runner for each target, not byte equality of a single RID produced on different host OSes.
- `.tar.gz` reproducibility is not established by this ticket.
- Complete publication includes `Microsoft.Extensions.Hosting.WindowsServices` 10.0.0 through `infrastructure/hosting/Hispania.Hosting.csproj`; Platform-only builds suppress that package with `PlatformOnly=true`. This is existing behavior and is not changed here. Complete ARM64 cross-publishing does not establish WindowsServices behavior or general application runtime acceptance on ARM64.
- Windows SCM installation still requires the complete Windows host and an elevated operator context. Platform-only has no Windows SCM service installation. Module contribution execution and production mTLS setup remain subject to the documented module authorization and deployment configuration contracts; this packaging change does not create or validate those capabilities.
