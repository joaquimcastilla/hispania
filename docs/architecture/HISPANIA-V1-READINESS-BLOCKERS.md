## Freeze §12 — Phase 1 blockers vs deferrals

§12 names the following blockers to Phase 1: (1) “No clean Core composition root/project/artifact exists; do not convert `apps/server`.” (2) “Core project allowlist and production artifact manifest are undefined.” (3) “The current server composition contains direct Media/Inventory/providers/demo dependencies; these must remain outside the new root.” (4) “Core empty boot/admin/persistence/module-list process journey has no acceptance test.” (5) “Admin bootstrap/auth boundary must be selected sufficiently to prevent an unauthenticated module install/disable API.” (6) “Product package/service/install layout and Core state/config paths need a Phase 1 design; developer launcher is not a production installer.” (7) “Fixture publisher must be explicitly trusted by the test operator; no general publisher or third-party ecosystem trust is implied.”

**R1 corrective note:** the sentence “All seven are BLOCKER BEFORE PHASE 1 IMPLEMENTATION” overstates the exact timing supported by the Freeze. §12 labels them “BLOCKER for Fase 1”, but §13 calls the Core composition root, artifact manifest and acceptance journey Phase 1 specification/deliverables, while §16 says entry gates are to be completed in a later, explicitly authorized Phase 1 preparation/implementation task. The Freeze does not unambiguously distinguish “before first code change” from “must be satisfied during Phase 1 before the corresponding feature/artifact is accepted or distributed.” R2 therefore withdraws the stronger pre-code timing claim; it does not waive any listed blocker or amend the Freeze. The owner must resolve the boundary in Owner Decision Packet question 2 before readiness can pass. The signed fixture trust policy is frozen in Owner Decision 9.2; no Core fixture or empty-boot test exists.

§12 expressly defers Media/Inventory extraction, full SDK packaging, PostgreSQL Core, full business roles/SSO, sustained Pi 4B qualification, WASM/hostile-native sandbox, Marketplace, Data Plane implementation, dynamic UI scripts and full cross-module backup/migration. Those deferrals do not waive required minimal Core authentication, secure bootstrap, provider-neutral Core persistence contract with SQLite, ARM64 smoke once an artifact exists, or Core-owned backup/restore boundary described in §§12–13.

### §12 seven-item timing classification

The Freeze's phrase “BLOCKER for Fase 1” is quoted as written. The following classification reads it together with §13 (“specification for the next phase”, “not implementation authorization”) and §16 (“entry gates ... in the later, explicitly authorized Phase 1 preparation/implementation task”). Where these sections do not fix an exact pre-code boundary, that uncertainty is an owner decision rather than a silently chosen interpretation.

Exact §12 requirements (Architecture Freeze §12, lines 967–975 at R2 source):

> - No clean Core composition root/project/artifact currently exists; `apps/server` is not to be converted in place.
> - Core-owned project allowlist and production artifact manifest have not been defined as build inputs.
> - The current server composition contains direct Media/Inventory/providers/demo dependencies; these must remain outside the new root.
> - Core empty boot/admin/persistence/module-list process journey has no acceptance test.

Exact §16 timing statement (Architecture Freeze §16, line 1109):

> “The following entry gates must be completed in the later, explicitly authorized Phase 1 preparation/implementation task:”

Its “Project changes expected” subsection (lines 1026 onward) says the host, manifest, process/fitness test project and packaging script are expected Phase 1 changes. Together these quotes make clear that Phase 1 is not authorized, while leaving the exact point inside preparation/implementation when each §12 blocker must be satisfied ambiguous.

The sole Debug failure explicitly required the independent Phase 18 historical reader generated by `tools/test-phase19-package-lifecycle.ps1`. That script was run in the temporary copy, where it passed 76/76 Runtime package-lifecycle tests and 2/2 Inventory package-backup tests. A subsequent full Debug run with `HISPANIA_PHASE19_OLD_READER` pointed at the generated temporary reader passed **219/219**. The TRX files and tracked-source copy remain outside the repository under `%TEMP%\hispania-r1-20261016`. **No harness or production code change was needed or made.** The reproducible safe invocation requires a repository-root layout, Debug configuration for helpers expected under Debug, and the historical-reader setup/environment used by the tests; it must not use an external `--artifacts-path` unless root discovery is made configurable.
