## Production installation and backup

Platform-only now loads `ProductionInstallation` for Windows x64, Linux x64 and Linux ARM64, verifies the installed artifact and configuration, provisions managed paths under `HOME/state`, applies production logging and trust policy, and retains the existing installation lock, staged binary switch, Phase 17 backup, verification and restore-based rollback. Platform-only is restricted to the server role and SQLite. It does not provision OS service accounts or systemd/Windows services; deployment remains an operator-managed offline operation.

The production composition initializes the Assets and Maintenance SQLite owners at first startup. Without that, a fresh install that had not yet called those endpoints lacked required stores and the existing backup procedure failed. No second backup or deployment system was added. Rollback after the new host has started uses verified backup restoration; schema rollback is not asserted. A same-version staging upgrade validates the mechanics, but is not evidence of an RC1-to-newer-version migration.

Local Windows x64 production lifecycle validation used a fresh, isolated temporary HOME and protected test secrets. The run on 2026-10-11 against the newly published artifact passed Deployment CLI install and `--check`, bootstrap, readiness, health, authenticated login, same-RID upgrade, Phase 17 backup verification, restore-backed rollback and login after restart. A first repeat used an older artifact and failed during backup; rebuilding a current artifact and repeating the lifecycle passed. The older artifact result is not evidence against the fresh package.

## Step 2.1-F — ModuleHost Jobs and administrative test token

This worktree now adds the experimental `IPlatformJobContributionV1` capability, optional signed manifest declarations, atomic contributions in the existing handler registry, and ModuleExtensionCatalog lifecycle integration. ModuleHost supplies module ID and generation; dispatch rechecks publisher authorization and active generation, acquires the catalog lease, and routes through in-process or existing out-of-process module execution. Deactivation/revocation drain and cancel cooperative work; Jobs remain Core-persisted and handlers remain ephemeral. Missing handlers fail terminally and require explicit retry after authorization is restored. The signed-package tests cover ModuleHost IPC, in-process execution/draining, signature and allowlist rejection, empty registry, undeclared module, duplicate batch, generation update and cancellation.

F1 diagnosis: the in-process fixture's generic `JsonSerializer.Deserialize<T>` used a DTO defined in the collectible fixture assembly. A controlled differential showed the fixture module instance was already collected and its handler revoked, while the ALC stayed alive with that serializer path; parsing the same opaque JSON via `JsonDocument` allowed the complete install/activate/register/execute/deactivate/revoke/unload flow to collect. The fixture now uses `JsonDocument`; this is a test-harness correction, not a production workaround. This demonstrates the trigger in the test, not the exact runtime GC root, and arbitrary trusted in-process module code can still retain references. The new unload assertion requires both module and ALC weak references to be dead. ModuleHost contribution tests: 9/9 passed; repeated in-process unload test: 5/5 passed. Full Runtime suite with the Phase 19 reader prerequisite: 218/219 passed; `HeldCallLeaseUsesConfiguredDrainTimeoutAndRecoversAfterRelease` timed out once during the full run and passed when immediately rerun alone (1/1). This remains a suite-level intermittent result, so F1 has focused passing evidence but not a clean full-suite pass.

F2 diagnosis: the harness launched the authentic RC1 server with a new `moduleAdminToken` property in `production.json`; RC1's strict schema correctly rejected that unknown property with exit code 2. The harness now leaves the RC1 schema intact, confirms its historical admin route is 503, then writes the new secret reference only after upgrading to the current artifact. It passes a random 256-bit token only through the isolated child process environment and verifies missing/invalid/correct bearer behavior on the new artifact. RC1 distribution upgrade tests: 2/2 passed against the authentic predecessor (`9b5abefe4c6b631360d505587748aedcb6c522d0`, manifest commit `9b5abefe4c6b631360d505587748aedcb6c522d0`). The new artifact resolves the configured `Modules:AdminToken` reference at startup. Release focused contribution tests: 9/9; Complete Release Server build: 0 warnings/errors. This closes the reproduced F2 harness/configuration issue, not the broader cross-platform Step 2.1-E gate.
