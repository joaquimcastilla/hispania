# Operating Experimental Dynamic Web packages

Dynamic Web reuses Phase 19 package trust, authorization, dependencies and recovery. It does not create a marketplace, fetch remote packages or grant permissions on installation.

Before install, verify the package publisher through the established trust configuration and explicitly authorize its package ID. Review requested permissions, backend code and the signed descriptor. Required UI needs host capability `hispania.web.contributions@1.0`; the exact Phase 19 host rejects required activation. Optional descriptors can be ignored by an older host. Schema 1 is Experimental.

Session-authenticated operators with `platform.admin` may upload a bounded archive to POST `/api/platform/admin/modules/packages` (raw archive body, maximum 128 MiB). The Server preflights and applies the existing package-set plan. A new package remains inert. POST `/api/platform/admin/modules/packages/<id>/enable`, `/disable` or `/uninstall` applies the existing lifecycle; dependency policy may reject the operation. Uploading a different version updates an installed package while preserving its enable policy. A failed health/activation restores the previous package set. No endpoint accepts an arbitrary filesystem path, and production legacy bearer mutation remains disabled.

Explicitly assign roles/permissions through the existing authorization administration. A package's namespaced declaration does not confer access; `platform.admin` alone does not grant `extensions.*`. Health components/actions additionally require `platform.observability.read`. Inspect Module Admin Web diagnostics or GET `/api/platform/admin/modules/web` for safe package/version/contribution/route/state/reason/count projections. Publisher trust revocation follows the existing package policy API/configuration; it removes UI eligibility along with backend eligibility.

To recover, stop the installation and use the Phase 17 offline backup/verify/restore commands and Phase 18 secret reprovisioning. Restore package state, keys/trusted IDs under the existing portable policy. Start the Server; its loader revalidates required descriptor bytes/assets and rebuilds the Web projection. No UI registry migration or npm command is needed at runtime. After distribution upgrade, verify `/readyz`, login, module health, UI diagnostics and a direct contribution route in both bundle configurations. A future optional schema must show Invalid UI with healthy backend; investigate rather than downgrading its schema number manually.

Reload existing browser pages after lifecycle changes to receive fresh navigation. Stale action/data calls fail immediately once a package is ineligible. Assets are public nonsensitive PNG decoration, served only while eligible with hash URLs, nosniff and no-store. Never use them for secrets.

Run `tools/test-phase20-dynamic-web.ps1` for local acceptance. Chromium and Node are build/test dependencies; the published Server runtime needs ASP.NET Core 10 and documented native Media dependencies, not Node. CI production tests also require privileged systemd/SCM fixtures and password-auth PostgreSQL. Local Windows success alone does not establish Linux support. Preserve TRX, browser traces/JSON, artifact checksums and the exact source SHA before claiming a CI result.
