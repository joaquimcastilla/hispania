# ADR-0029: Single-Coordinator Distributed Work Foundation

Status: Accepted; generic transport, transactional single-coordinator recovery, scoped media transfer, and remote FFmpeg Playback path are implemented and locally process-tested. Physical second-host verification remains pending.

## Context

HISPANIA needs to place eligible capability operations on explicitly authorized remote workers without making capability consumers depend on worker implementations or network details. The existing local module host protocol is process IPC and must not be exposed on a network.

## Decision

- Contracts identify work by stable job ID, exact capability contract ID/version, correlation ID, and opaque JSON payload. Capability-specific payload meaning stays with the public capability contract.
- Worker inventory reports OS, architecture, CPU, advisory memory, concurrency, accelerator labels, and exact capability versions. Inventory never authorizes a node.
- A single coordinator owns node authorization, job state, lease generation, and result publication. Worker enrollment is explicit. Capabilities are separately allowlisted for each node.
- Remote assignment is opt-in per operation and rejects operations marked as having external side effects. Automatic recovery is allowed only when the caller declares retry safety and no external side effects.
- Each reassignment increments the fencing generation. Completion must match the current worker and generation. Expired unsafe work becomes `Uncertain`, since a lost connection cannot prove the worker stopped.
- The initial scheduler uses exact contract compatibility, current heartbeat, enabled/authorized state, concurrency, and a deterministic preferred-node/ID order. Hardware labels are advisory and do not imply codec/profile compatibility.
- The server uses a transactional SQLite state snapshot store with an exclusive coordinator lock file. The in-memory state store remains available to tests and temporary deployments. Startup invalidates leases, returns only retry-safe/no-side-effect work to Pending, and marks other interrupted work Uncertain while preserving generations.
- Remote workers use a distinct HTTPS/mTLS JSON transport, SHA-256 certificate pin enrollment, explicit per-node capability allowlists, validity/EKU checks, bounded request bodies and negotiated protocol versions. The local OutOfProcess framing protocol is not a network listener and is not reused as one.

## Guarantees and limits

Implemented locally: capability allowlists, bounded inventory/payloads, HTTPS client-certificate transport, pin-based enrollment/rotation/revocation, protocol negotiation, generic separately launched agent integrated with the existing OutOfProcess extension host, heartbeat/lease renewal/cancellation instructions, safe retry policy, SQLite transaction/restart recovery and generation fencing. A generic media broker issues a short-lived transfer grant only to the active leased node; grant secrets are fetched over mTLS when the lease is active and are not stored in the persistent job payload. Source reads are seekable, range-limited and aggregate-capped; result writes are size-limited, SHA-256 checked, staged separately and published under opaque handles. `FfmpegCompatibleMediaTranscoder` supports `Local` (default), `RemotePreferred` and `RemoteOnly`, queues a retry-safe versioned FFmpeg capability request, imports and validates the published result into its normal opaque cache, and applies explicit local fallback. The agent's optional FFmpeg capability handler reuses `Hispania.FFmpeg.Worker`, its process timeout/resource policy, and software codecs. A process integration test exercises the Playback HTTP stream endpoint over a separately launched mTLS agent, validates output with ffprobe, kills the agent during a blocked source transfer, verifies local fallback and then tests stale-generation rejection/recovery.

Not implemented or verified: one-time enrollment credentials (operators provision thumbprints out of band), PostgreSQL-backed distributed state, administrator audit trail, a process kill specifically while FFmpeg is encoding, Linux Actions result, and two physical-server verification. Broker tests cancel an upload deterministically; the process integration transcodes MPEG-4 with real FFmpeg, interrupts the agent's result-upload request, verifies cancellation and cleanup, and separately kills the agent during source transfer. They also reject a lease that expires before final publication; the endpoint removes an artifact if coordinator completion is fenced. A process crash in the narrow interval after atomic file publication but before the SQLite completion transaction can leave an unreferenced artifact until its 24-hour cleanup; it is not returned to Playback and a retried generation receives a new grant. SQLite mode intentionally excludes concurrent coordinators. No exactly-once claim is made. Playback defaults to local processing and remains functional without remote nodes.

The generic media-transfer broker is server-side and capability-neutral. Its worker authorization requires mTLS identity plus the active job lease and generation; a random grant ID is in the work payload while the bearer secret is returned only by a separate active-lease endpoint and is not persisted with the job. Source bytes and published artifacts are process-local and expire; a retried generation obtains a fresh grant after restart.

Server configuration: set `DistributedWorkers:StatePath` (environment form `DistributedWorkers__StatePath`) to an access-controlled persistent SQLite path. Default: `%LOCALAPPDATA%/Hispania/distributed-coordinator.sqlite` on Windows or the platform LocalApplicationData directory. The sibling `.coordinator.lock` must remain writable and held by the sole coordinator. Set `DistributedWorkers:Transcoding:Mode` to `Local` (default), `RemotePreferred` (fallback to local after remote failure or a 10-second unassigned queue), or `RemoteOnly` (return unavailable when no remote result is produced). Set `DistributedWorkers:TransferPath` to the protected staging directory and `DistributedWorkers:TransferStorageBytes` to its aggregate storage ceiling (default 40 GiB). Each source grant caps aggregate reads at three source lengths; each result grant caps aggregate upload attempts at twice the result ceiling. Admin authorization pins each node's client-certificate SHA-256 fingerprint; the certificate must be valid and carry clientAuth EKU. Rotate by updating the pinned fingerprint and reconnecting the node; revoke/disable through the authenticated admin routes. Workers validate the coordinator server certificate against configured SHA-256 pins.

To configure a second machine, install the matching .NET 10 runtime, FFmpeg and (on Linux) `prlimit`; copy the published `apps/worker-agent` output including `ffmpeg-worker/`; provision a client PFX with a private key and clientAuth EKU; add the node ID, FFmpeg capability `hispania.transcoding.ffmpeg.remote@1.0`, and SHA-256 certificate fingerprint through `POST /internal/admin/modules/remote-workers/{nodeId}/authorize` with body `{"allowedCapabilities":[{"contractId":"hispania.transcoding.ffmpeg.remote","contractVersion":"1.0"}],"certificateThumbprint":"<64 hex SHA-256 characters>"}`; then configure `DistributedWorker:CoordinatorUri`, `NodeId`, `ClientCertificatePath`, `ClientCertificatePassword`, `CoordinatorCertificateSha256Pins`, `Ffmpeg:Enabled=true`, `Ffmpeg:ExecutablePath`, and a private `Ffmpeg:CachePath`. Keep worker and coordinator clocks synchronized. No library path is configured on the worker. Remote mode uses software `libx264` or stream copy and does not assume a GPU. Validate a real network deployment separately; local process integration is not physical-host verification.

## Two-computer validation runbook (Windows coordinator, Linux worker)

This is a reproducible procedure, not evidence that physical-machine validation has already run. Use a private LAN or VPN. The coordinator owns the media library, SQLite database and transfer directory; the worker receives only the authorized source bytes and has no library-root configuration. Keep both hosts patched, time-synchronized and operator-controlled. Process isolation and FFmpeg resource limits contain crashes and bound configured resources; they do not sandbox hostile code. Certificate pinning authenticates the configured peer; it does not make an authorized worker trustworthy with respect to its own operating system.

1. **Prepare certificates.** Use an organization CA or a dedicated offline test CA. Issue a coordinator TLS server certificate with `serverAuth` EKU and SAN for the DNS name the worker will use. Issue a distinct worker certificate with `clientAuth` EKU and private key; export its leaf certificate and private key as a password-protected PFX readable only by the worker service account. Install the server certificate and key on the coordinator's HTTPS listener. Record the SHA-256 of the coordinator leaf DER certificate for the worker pin and the SHA-256 of the worker leaf DER certificate for coordinator authorization. Never copy the CA private key or worker private key to the other machine. Example fingerprint calculation: `openssl x509 -in worker.crt -outform DER | openssl dgst -sha256`; for the coordinator, run the same command on its leaf certificate. The values are 64 hexadecimal characters without separators.
2. **Expose the smallest network surface.** Bind the coordinator's existing HTTPS listener to a LAN/VPN address and one chosen TCP port (example `7443`). Allow inbound TCP to that port only from the worker's source address at the host firewall and network firewall. The worker needs outbound TCP to the coordinator. The worker opens no inbound listener, so do not create a worker-side inbound rule. Keep `/internal/admin/modules/*` restricted to the trusted administration network at the firewall or reverse proxy; its bearer token is separate from mTLS. Do not expose the server's HTTP listener to the worker.
3. **Configure coordinator storage and playback.** Set `DistributedWorkers:StatePath` and `DistributedWorkers:TransferPath` to protected persistent directories with sufficient free space; configure `DistributedWorkers:TransferStorageBytes` to the intended enforced aggregate ceiling, `DistributedWorkers:MaximumResultBytes`, and `DistributedWorkers:Transcoding:Mode=RemotePreferred`. Retain the coordinator's `.coordinator.lock`; only one server process may own the distributed state database. Configure a stable HTTPS address and the server certificate. Restart the coordinator and verify its HTTPS certificate from the worker network before authorizing a node.
4. **Authorize the worker.** Install the matching .NET 10 runtime, FFmpeg with `libx264`, and `prlimit` on Linux. Publish/copy the worker-agent directory including `ffmpeg-worker/` and any required contract assemblies. On the coordinator, call `POST https://<coordinator>:<port>/internal/admin/modules/remote-workers/<nodeId>/authorize` with the admin bearer token and JSON body `{"allowedCapabilities":[{"contractId":"hispania.transcoding.ffmpeg.remote","contractVersion":"1.0"}],"certificateThumbprint":"<worker DER SHA-256>"}`. Protect shell history and process logging if the bearer token is supplied on a command line; prefer a secret-aware HTTP client. Confirm the response and use authenticated `GET .../remote-workers` to inspect its connected state and discovered capability after the worker starts.
5. **Configure and start the agent.** Provide `DistributedWorker:CoordinatorUri=https://<coordinator>:<port>/`, `NodeId`, `ClientCertificatePath`, `ClientCertificatePassword`, `CoordinatorCertificateSha256Pins__0=<coordinator DER SHA-256>`, `Ffmpeg:Enabled=true`, `Ffmpeg:ExecutablePath`, and a private `Ffmpeg:CachePath` via the service's protected configuration/secret store. Set `MaximumConcurrentJobs` to the intended value; the FFmpeg policy clamps it. Start `Hispania.WorkerAgent` as a dedicated service account and verify its startup log contains the expected node ID and capability, but never log the PFX password or transfer bearer. The worker should have no configured path to the coordinator's media library.
6. **Verify transfer and Playback.** In authenticated `GET .../remote-workers`, confirm the node is connected and the exact `hispania.transcoding.ffmpeg.remote@1.0` capability is advertised. Request a media item that requires transcoding through the normal Playback stream endpoint. Verify the coordinator reports a completed job, Playback serves `video/mp4`, and `ffprobe` on the received response reports the expected streams/container. Check coordinator transfer storage and worker private cache; both should remain within configured bounds.
7. **Exercise recovery.** Start a large transcode and stop the worker service during source transfer; confirm the job is cancelled/fenced or safely requeued according to its declared retry policy and `RemotePreferred` serves only after its explicit local fallback. Repeat during encoding and result upload. Restart the worker and confirm it reconnects, advertises capability, and receives a newer lease generation; verify no prior generation can complete. Restart the coordinator only after stopping it and releasing the SQLite lock, then verify retry-safe work recovery and `Uncertain` status for unsafe work. Finally repeat with `RemoteOnly`; with the worker unavailable, Playback must return unavailable and must not invoke local FFmpeg. Record OS versions, certificate fingerprints (not private keys), job IDs, generations, state transitions, and `ffprobe` output.

Physical Windows-to-Linux execution, interruption during the FFmpeg encode itself, and a current Linux/Windows Actions run remain pending. The test interrupts a real remote job during result upload, but does not kill the worker process while the encoder is active. Do not mark the phase closed until required validations are performed and their run IDs/SHA are recorded.
