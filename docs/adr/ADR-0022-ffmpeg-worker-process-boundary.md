# ADR-0022: FFmpeg Worker Process Boundary

Status: Accepted

## Context

Playback must not expose filesystem paths or keep transcoding orchestration inside the HTTP host. The source provider already offers read-only content streams; FFmpeg needs a bounded process boundary and safe recovery from a failed job.

## Decision

- Keep `ICompatibleMediaTranscoderV1` selected through the existing capability registry at host startup.
- Return a `TranscodedContentHandle`, content type and length. The host serves generated bytes via `ITranscodedContentStore`; the handle is an opaque cache key, never a path.
- Launch `Hispania.FFmpeg.Worker` as a process per job. The V1 JSON request/response is versioned as `hispania.transcoding.ffmpeg.worker@1`; source bytes use redirected stdin, status uses stdout, and diagnostics stay on stderr.
- Only the worker interprets its configured cache directory and FFmpeg executable. It writes a unique partial file and atomically publishes the completed MP4 under a validated cache key.
- `Playback:Worker` configures maximum concurrency, wall-clock job duration, cache ceiling, per-job output ceiling, memory and CPU-time ceilings. The host enforces the wall-clock timeout, kills the process tree on timeout/cancellation, retries a failed job once from a newly opened source stream, and resumes on later requests by starting a fresh worker.
- Host and worker share the configured derivative cache. This is an operational shared-volume dependency.

## Isolation and limits

- **Logical isolation:** playback and source access communicate through public contracts; paths and EF entities are absent from the worker protocol.
- **Process isolation:** FFmpeg and its worker orchestration run outside the web host. This limits crash propagation and enables process-tree cancellation.
- **Resource controls:** Windows uses a Job Object for process/job memory, configurable CPU rate/time, active process count and kill-on-close. Linux starts the worker under `prlimit` with address-space, CPU-time and file-size limits and sets the .NET GC heap ceiling. FFmpeg also receives an output-file limit; the host prunes derivative cache toward its configured ceiling. These are OS-enforced resource controls, not a security sandbox.
- **Limits:** the temporary-storage setting is divided among concurrent jobs and bounds each output file. Linux `RLIMIT_FSIZE` is likewise per file, not a cgroup quota for all descendants. Neither platform quotas the whole cache volume, filesystem metadata or unrelated processes. Cache pruning is best-effort. Workers still run under the host identity, inherit its environment and share the cache; no dedicated identity, filesystem ACL boundary, seccomp/AppContainer profile or untrusted-code sandbox exists. Local Windows acceptance tests attached the Job Object and ran real recovery/media cases; they have not deliberately exceeded all resource limits. Linux `prlimit` awaits a run of the updated Ubuntu workflow.
- The worker is per job, not a persistent service. No heartbeat, load balancing, hot swap, production A/B, or process sandbox is claimed.

## Consequences

Worker protocol and contract tests run without FFmpeg. Integration/recovery tests cover successful encoding, crash, timeout, cancellation, publication failure, partial cleanup, retry and cache idempotency. A failed worker launch followed by successful encoding, cache reuse and HTTP range delivery are tested when FFmpeg is installed. Six recovery/media tests pass locally on Windows with real FFmpeg; current-tree Ubuntu CI remains pending. Correlation trace IDs are forwarded through V1; metrics cover attempts, failures, retries, cancellations, active jobs, duration and process resource observations. `/healthz` remains server health; `/internal/capabilities/transcoding/health` reports optional transcoding capability health. Deployment must include the worker runtime files beside the server and provision a shared cache directory.
