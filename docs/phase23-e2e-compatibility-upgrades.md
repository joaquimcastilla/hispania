# Phase 23 — End-to-End Compatibility, Upgrade and Rollback Validation

## Scope and result

Phase 23 integrates the existing Phase 14–22 compatibility, migration, backup, package, web, security and maintenance gates. It adds a read-only provenance checker, a scenario manifest and one local gate runner that captures its outputs under `.artifacts/phase23/`. It does not introduce a new production migration/versioning mechanism or business feature.

The authenticated historical corpus actually available at the accepted Phase 22 base contains the Phase 14 technical baseline (0.7), 27 selected source/binary/wire/package artifacts and 15 populated owner data artifacts. These fixtures originate at `78f291fdacf9442c6e2d8e23094dc0e309828693`. They are checked byte-for-byte against their frozen manifests. They are never regenerated by the Phase 23 gate. The tree does **not** contain complete runnable release snapshots for every phase 13–22; these phases must not be represented as separate historical distribution versions. Phase 19/20 gates instead build specific readers from their recorded predecessor SHAs and exercise those readers with deterministic local packages.

## Architecture and operation

`compatibility/phase23-upgrade-matrix.json` describes the available historical identities, limitations, supported test paths, storage engines, package/module sets, schema transitions, expected data invariants, warnings and fail-closed conditions. `tools/phase23-compatibility-inventory.py` verifies all 27 Phase 15 and 15 Phase 16 artifact hashes and manifest cardinality without writing to the source corpus. `tools/test-phase23-e2e-compatibility-upgrades.ps1` records the exact tested worktree SHA and runs the applicable predecessor gates in isolated artifact directories. The gate does not delete its evidence. All destructive fixture tests use copies/temp roots from their existing test harnesses.

Run from the Phase 23 worktree:

```powershell
pwsh -NoProfile -File tools/test-phase23-e2e-compatibility-upgrades.ps1
```

Results include the fixture inventory, gate logs/TRX files, per-gate evidence, `phase23-summary.json`, and the exact `phase23-target-sha.txt` under `.artifacts/phase23/`.

## Preserved data and compatibility axes

The Phase 16 populated fixtures cover users, credentials/sessions and permission meaning; events, delivery and dead-letter state; jobs and idempotency; Assets and stored bytes; audit rows; coordinator generations/fencing/leases; Inventory records and opaque Asset references; Media catalog/metadata/path records; and playback configuration/snapshots, each only where present in its historical schema. Owner-specific assertions verify counts, identities, relationships and relevant payload/state, repeat-open idempotency, schema ledgers and checksums. Phase 22 regressions cover retained package known-good state, coordinator high-water generations, backup/restore, maintenance state and protected HTTP operations.

The combined existing gates exercise selected HTTP contract semantics, frozen source/binary consumers, signed packages and IPC/worker protocol fixtures, production configuration/secrets, declarative web contribution compatibility, backups/restores, package lifecycle and rollback/known-good retention. These are intersecting targeted guarantees, not universal compatibility across every endpoint, client, worker binary or configuration ever produced. No contract is made Public Stable by Phase 23.

## Recovery and rollback semantics

Historical schema safety tests run actual child processes killed during SQLite DDL/data/ledger work under DELETE and WAL journaling and check SQLite recovery and untouched historical rows. Other tests cover exception rollback, multi-hop migrations, concurrent process serialization, malformed/future schema fail-closed behavior and byte-preserving rejection. Backup/disaster tests run against isolated copies and real process hosts. Phase 19–22 tests cover package current/known-good retention and restore behaviors.

Rollback is forward-migration safety plus owner-level backup/restore and package retention. It is **not** a guarantee that an old server binary can safely open a database after a newer binary has migrated it. Restoring across stores is not globally atomic. Process-termination tests do not simulate physical power loss, storage-controller failure or every external filesystem race.

## Configuration, security and evidence

Configuration schema generation and secret handling are exercised by the Phase 18 suite; Phase 21 runs security hardening and canary scans on its captured logs/results. Artifacts are synthetic, fixture roots are isolated, and no real media library or production database is used. Phase 23 evidence lives in `.artifacts/phase23/`, which is ignored by Git. Before publishing evidence, inspect it for secret material; the Phase 21 canary scan covers its own captured outputs.

## Local validation and pending CI

The dedicated Phase 23 gate chains Phase 15 compatibility, Phase 16 historical upgrade, Phase 17 backup/restore, Phase 19 package lifecycle, Phase 20 dynamic web, Phase 21 security, and Phase 22 maintenance gates. Each underlying script requires its declared cases to be discovered and pass without skips. The dedicated script does not silently treat unavailable services as passes. PostgreSQL, privileged native service installation (Windows SCM/Linux systemd), cross-platform behavior and CI artifact publication still require their respective configured runners. Run broader full-solution, platform-boundary, web Modern/Classic, dependency audit and platform-specific production gates independently before claiming implementation ready for self-hosted CI.

## Residual limitations

- There is no universal binary rollback after schema upgrade.
- There is no global atomic upgrade/restore across independent stores.
- Complete historical server installations and a full historical WorkerAgent binary matrix are unavailable.
- Unknown/future schema, package or wire generations reject closed where covered; no automatic upcasting or exactly-once effects are claimed.
- SQLite child-process death is tested; physical power-loss durability is not.
- External filesystem races and HA/multi-master behavior are outside this evidence.
- PostgreSQL live and Windows SCM/Linux systemd remain pending unless executed on matching configured runners.
- This phase makes no exactly-once event/job delivery claim.
